# Schema 版本前置保护：审查与暂停方案

结论：本阶段仅报告方案，未保留生产代码修改。`src/store.mjs` 的工作树差异为空。兼容性判据尚未确定，直接将所有无版本非空库视为陌生库会破坏既有历史夹具；仅凭 Git 中缺少版本 4 的提交就拒绝版本 4 同样缺乏依据。

## 已确认的风险

- `open()` 先创建父目录并打开数据库，随后设置 `journal_mode=DELETE`、执行 DDL、运行 occurrence 迁移，之后才读取 `meta.schema_version`，最终无条件写入 7。未来版本可能先被修改再遭降标；畸形值通过 `Number()` 转换后也可能被覆盖。
- `test/occurrences.test.mjs` 约 105 行构造只有 `memories` 且无版本的历史夹具；本次仅读取，未运行旧测试。它证明“非空且无版本”不能一概视为陌生库，但单凭形状相同也无法证明陌生库就是历史库。
- 历史提交 `8e9413f` 的 `src/store.mjs` 提及 v4，原逻辑对数值版本小于当前版本执行迁移。仅凭当前可见提交中没有版本 4 的常量定义，不能断定它不受支持。
- 当前迁移包含独立 `BEGIN IMMEDIATE`、DDL 和多次写入，并非整体原子；迁移失败后可能保留先前步骤。检查成功并不代表迁移可回滚为原状态。

## 候选设计及未决条件

同一连接先设置 `locking_mode=EXCLUSIVE`，以 `BEGIN EXCLUSIVE` 获取锁，在任何 `journal_mode`、DDL 或迁移前读取并严格校验版本；提交读取事务后保留排他锁，执行现有初始化，完成后恢复 `NORMAL` 并确认锁确实释放。对未来值、畸形值及结构异常应在变更前报错，避免以数值宽松转换后覆盖；明确接受的版本集合和缺版本识别规则须先依据真实历史契约确定。

仅在本机 Node v24.22.1、临时合成库上做了一个原始 SQLite 锁探针：DELETE 和 WAL 各自设置排他模式并执行 `BEGIN EXCLUSIVE`、读取、`COMMIT` 后，第二连接的 `BEGIN IMMEDIATE` 均报 `database is locked`；原连接随后切到 DELETE 成功。它没有覆盖 `store.open()`、正常模式恢复后锁释放、Windows 多进程、SQLite 其他版本、只读连接、故障注入或异常清理，不能推广为跨环境保证。WAL 下关闭连接可能涉及检查点及辅助文件变化；失败后需分别验证逻辑状态及 journal_mode，不能等同于磁盘字节完全不变。

打开路径本身可能创建空文件或父目录，且非 SQLite 客户端直接替换文件、网络文件系统锁语义、外部不遵守锁协议的操作都不受该方案保证。版本验证与迁移必须在持锁期内完成；锁释放前后及并发打开需要独立验证。新空库与无版本陌生非空库要区别，已知历史结构应按可证据化的精确签名验证，签名匹配也不能证明来源；若兼容与防误认存在无法消除的冲突，需明确产品策略。

## 后续验收

单独建立仅导入 `store.mjs` 的临时 SQLite 合成测试，干净进程环境且不访问真实配置、数据库、密钥或网络；覆盖未来版本、畸形值、空库、已证实 legacy、重复打开、未知非空库、DELETE/WAL 与并发竞争，并在失败后检查逻辑状态和日志模式。额外确认模块依赖及导入副作用、恢复普通锁后的多连接行为、锁获取失败资源清理，以及不同受支持 Node/SQLite 环境。现阶段未实现保护，也未运行上述 store 测试。
