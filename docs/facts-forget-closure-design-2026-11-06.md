# 历史 facts 遗忘闭环设计

当前结论：保留所有持久 facts 的启动拒绝。历史 TEXT 键关联 memories.id；历史 INTEGER 键关联当时 memories.rowid。INTEGER 的值域及行号重用使仅凭当前同值关联无法证明归属。已出现孤儿或未经验证的迁移史时，后来的同号行可能属于其他记忆。L1 从现有正文重新抽取的事实是派生投影，既不是历史 facts 的替身，也不是历史事实完整性的证据。

现有 index.mjs 遗忘事务只删除 segments 和 memories，提交后重建内存 facts；store.raw() 暴露可写连接，调用者能绕开工具删除路径、创建 facts，另一数据库连接也能在启动事务结束后变更数据。因此把 DELETE facts 加进单个工具事务尚不足以形成闭环。启动 BEGIN IMMEDIATE 只保护该事务期间的检查和迁移，不提供运行期的全局排他。

建议方案：明确历史事实的产品语义和保留要求，先在隔离副本验证数据来源及每条键的唯一归属；证据不足的库继续拒绝并输出可诊断原因。必要时使用离线、可审计的人工映射及备份，不应靠文本相似度或重建 L1 静默推断。若允许持久保留，建立受控删除边界：收敛 raw 可写能力及其他连接访问，或由验证过的数据库级机制保证所有删除路径同时清理；严格核查触发器、约束、类型、孤儿、冲突和表结构，并评估修改与删除后侧文件及备份的遗留。将事实、段表、记忆和关联数据统一置于同一写事务，失败完整回滚，提交失败及重建失败进入故障态；防止并发写入与检查/使用间竞态。放行前应覆盖 ID 精确删除、批量、dry-run、raw 绕行、故障注入、重启、并发、INTEGER 重用、非法类型和回滚，并验证历史数据按原值隔离于 L1。

本次新增合成回归只证明 raw 同连接绕过、INTEGER 孤儿重用歧义、事务期间排他；并非现有系统支持历史库的证明，亦未验证运行期对其他连接的约束。
